# U9 next contract: preparation authority must survive through commit and handoff

Status: **READY_FOR_CONTRACT_REVIEW**. Report-only source reconciliation, 2026-10-02. No implementation or acceptance execution is claimed.

## Architecture overview and scope

Implement one missing predicate in the existing preparation coordinator:

> A preparation may replace its durable row or hand off a new child action only through its current, process-local capability holding that run's actual OS lease, against the last successfully committed row revision. A storage failure or lost capability closes that authority until continuity is explicitly reconciled. A stale callback cannot write, dispatch, reset spending, or release a successor's lease.

This is a preparation-row and preparation-to-job admission fence. It is not a new task engine, general corpus acceptance authority, distributed lock service, provider incident ledger, or complete U9 implementation. In particular, preventing a *new handoff* is different from stopping an already accepted child or proving an external resource is free.

The relevant architecture is preparation → action catalog/job store → provider/compiler adapters, with pure admission/retry accounting embedded in preparation JSON. Preserve those boundaries and public action names. Operations continue through the existing 8080 catalog when separately authorized; this report made no live calls. The future implementation must corroborate serving-source ownership before Python edits under AGENTS.md.

## Concrete missing predicate and failure traces

1. `_write(row)` accepts any supplied snapshot and resolves the *current* workspace dynamically. It neither requires the lease nor compares row revision/owner generation. An old callback can overwrite newer spending and checkpoints after another generation resumes. Several calls also occur outside `_LOCK` (`stopped`, end-of-workflow); an RLock is process-local in any case.
2. The MCP capability checks authority, but `execute.action` reserves and calls `jobs.start_job` for non-MCP actions without the corresponding current-lease check. It leaves `_LOCK` between durable intent and handoff. A stale action can therefore create a new job even though the nested MCP guard would refuse a remote call.
3. `control` reads a snapshot and, at `preparation.py:2414–2417`, writes a revised deadline before `submit` acquires the OS lease. A concurrent allocation revision/resume can be overwritten. Queued admission writes at `:564,:568,:575` and legacy supersession at `:879` also bypass per-row lease ownership.
4. `_release_lease(run_id)` pops by ID, not expected identity. `execute`'s finalizer writes then discards `_ACTIVE` and releases by ID (`:1962–1975`). A stale finalizer can disturb successor state; conversely a failed final `_write` skips cleanup entirely. The parallel matching pool can use `shutdown(wait=False)` on interruption (`:1894–1910`), so late work is a concrete callback boundary worth qualifying.
5. Failed MCP `_write` refuses that call but does not poison the capability. A later successful write can resume using the same mutable snapshot without an explicit continuity decision. General writes have no stable authority-loss outcome; broad error handling attempts another final write.

These are source-derived failure mechanisms, not observed live incidents. The selected slice closes these preparation-local paths; it does not infer missing architecture solely from naming.

### File ownership and dependency direction

One implementer owns the following narrowly bounded source seams: `src/agentdecompile_recovery/corpus/dashboard/preparation.py` (authority, birth witness, row/receipt commit and lifecycle); `actions/jobs.py` (private root handoff and typed failure projection); `workflow.py` (short canonical-state mutation callbacks only); `react_api.py` (existing direct preparation endpoint's refusal adapter); and `workbench.py` (existing open/register preparation-result projection). These latter paths are under the same dashboard directory. No frontend assets, schema DB, matcher, compiler, provider protocol or generic retry-policy rewrite. Add a focused future acceptance file `tests/test_preparation_authority.py`; adjust the existing preparation accounting fixtures to acquire authority honestly. Existing pure `admission_budget.py`, `mcp_budget.py` and `retry_policy.py` semantics are retained.

Keep authority helpers private to preparation. Pass a private callable/object to jobs as already done for `_mcp_reserve`; jobs must not import preparation authority classes into module-global initialization. Do not serialize capabilities in job params, argv, environment or receipts. This maintains the existing dependency direction and avoids a new circular dependency or public SDK contract.

### Capability and row identity

Use a private `_PreparationAuthority` created only after actual OS lock acquisition. It binds run ID, frozen preparation directory/workspace identity, exact lease handle, owner host/PID/start identity, unique generation, last committed `rowRevision`, canonical in-memory row, a per-authority reentrant gate, and state `current`, `continuity_required`, or `revoked`. The durable row gains a small `authority` metadata record `{schema:1,generation,rowRevision}`; these are continuity comparisons, not credentials. Do not equate generation, objective ID, action ID, allocation revision or process identity.

A capability registry must compare object identity, not merely equal fields. Execute receives the exact capability for its root job; it cannot look up a replacement by run ID. Matching callbacks and MCP reservations capture that same object. A capability cannot be constructed by reading JSON. New generation is minted only while owning the physical lock; budgets/retry histories are copied forward unchanged after validation.

### Exact first-slice eligibility and continuity witnesses (DA-1)

The bounded positive domain is genuine first creation in a qualified new preparation namespace, followed by healthy continuation within the **same authority session**. An authority session is an unforgeable process-local object created by the authority implementation, not a PID, host boot ID or serialized UUID. Reimport/replacement that loses that object is authority-session loss even in the same PID. No historical process-restart or general legacy migration is enabled by this slice.

Introduce one small creation witness owned by preparation: an append-only `.preparation-authority-births-v1.jsonl` in the frozen workspace root, outside `preparations/`, protected by its own nonblocking OS lock. Its first record is `{schema:1,kind:"namespace",namespaceId}`; each later record is `{kind:"objective-issued",runId,birthSessionId}`. No budgets or command credentials are stored there. `_issue_new_objective` is the sole producer. Before constructing an empty budget or starting work, it appends and durably flushes the unique issuance record, fsyncs the directory as required, and returns a private `_NewObjectiveWitness` retained in memory. Its identity binds namespace, frozen root, run ID and authority-session object. It is single-use for initialization, with the successful initializer replacing it by a healthy continuity witness. JSON issuance records are tombstones/discovery facts, never capabilities.

Bootstrap the birth log only while exclusively holding its namespace lock and only when neither the log nor `preparations/` exists; use exclusive creation, durable initialization, then create `preparations/`. Refactor `_directory` so observation does not implicitly create it before this check. A preexisting preparations directory without a birth log is a legacy/unknown namespace and stays read-only. Do not silently bootstrap it from a directory scan. The log is never truncated, replaced from an old snapshot or deleted by ordinary preparation code. Parse/validate the complete issued-ID set before issuing a new ID; duplicate/conflicting/malformed records refuse. A partial append or failed flush closes new issuance for that namespace in the current session. No work may start until issuance and initial row both commit. Log unavailability blocks *new issuance*, not a healthy independently witnessed authority's existing row operation unless its own continuity inputs fail.

#### No-effect namespace contention (R1-1)

At the **namespace-lock acquisition call only**, catch a confirmed lock-contention `BlockingIOError` before the generic `OSError` conversion. Translate it to private `_PreparationIssuanceWait(Exception)`, distinct from `_PreparationAuthorityRefused`. This case is eligible only before this invocation has performed any issuance append/bootstrap write. It creates no birth record, private witness/capability, ledger initialization, row, fault latch or execution-capacity slot. Opening/closing the lock descriptor is not issuance. The namespace lock adapter must distinguish the platform's actual busy-lock result from permission/descriptor/device failures; the existing Windows helper's broad OSError-to-BlockingIOError conversion (`preparation.py:198–201`) cannot be reused as proof of contention without preserving/classifying its underlying cause. Unknown acquisition failure follows the storage-error path. Do not classify `BlockingIOError` from later append/flush/fsync as lock contention; after writes begin, every uncertain failure keeps the persistence-fault latch.

The sole projection adapter below accepts this wait type and returns HTTP **409** with exactly the normal bounded identity/reason fields plus `ok:false`, `status:"waiting"`, `nextAction:"preparation_issuance_busy"`, `wakeCondition:"birth_namespace_lock_available"`, `phase:"initialization"`, `retryable:true`, `retryAfterSeconds:1`, `noEffect:true`, `durable:false`, and null generation/last committed revision. Use reason/error `Preparation namespace issuance is busy; retry after the namespace lock becomes available.` This is neither accepted admission (202) nor persistence failure (503), and it requires no continuity repair. No capability, log content or arbitrary context enters the body.

Make at most one nonblocking acquisition attempt per invocation. Return immediately after releasing/closing the unsuccessful lock descriptor; hold no authority gate, preparation registry/global lock or job-store lock while attempting/waiting. Birth issuance must be called before acquiring those locks or a run execution slot. Callers do not sleep/retry synchronously. A later request may retry after at least one second; maintain a bounded namespace-level monotonic next-probe timestamp in the existing admission worker so repeated wake events do not form a busy loop. The worker makes at most one namespace-lock probe per namespace per second, without a new thread/timer per waiting objective. Its existing periodic poll is a permitted slower retry. Lock release may set the existing admission wake, but is merely a hint and never grants authority.

Every retry reacquires the namespace lock and revalidates the complete log, supported namespace/schema/session rules, issued-ID set and current row predicate. An ID issued in the meantime becomes same-session observation/continuation only with its retained private witness; otherwise the established-ID refusal rules apply. Never append the same ID twice or use an earlier negative membership result. No ordinary contention retry can clear a preexisting fault/over-limit restriction. If this is a direct client/open request without an existing durable inventory request, the response promises only retry eligibility: it does not silently create a durable queued objective or claim eventual automatic admission. Existing inventory requests remain present and unacknowledged for the bounded polling consumer.

The adapter may expose only `limitKind` (`bytes`, `record_bytes`, or `issued_ids`) and its numeric `limit`, never log contents. Preserve every existing tombstone and refuse new issuance for that namespace; do not truncate, compact, rotate to a new namespace, delete records or reset an objective to evade a cap. Suppress automatic issuance retries at this limit until the named future qualification, but do not poison healthy existing private witnesses or block their row work. Full-ledger corruption and storage-write uncertainty remain distinct faults. Unlimited namespace growth, indexing and compaction are outside this slice.

This is a witness independent of the replaceable preparation row, not an independent disaster-recovery store. Its append-only/cooperating-writer assumption and the fresh-namespace bootstrap must be qualified before activation. Losing/restoring the whole workspace or both log and rows is outside this first slice: no automatic restore/clone activation is supported. A later restore gate must corroborate namespace incarnation outside restored data. No claim that absent files alone can detect an unannounced rollback is made.

`_HealthyContinuityWitness` is produced only by a successful initial commit or guarded `_write` in this session. Retain the exact committed row snapshot, both full ledger/reservation maps, allocation revisions, attempts, generation/revision and frozen root. A clean coordinator retirement retains this witness after releasing the physical lease. Healthy resume acquires a new real lease and compares the full on-disk authoritative row to that retained committed snapshot, not just counters/revision; only permitted separately versioned control fields are merged afterwards. ### Private APIs and mutation linearization

- `_write(row, *, authority)` becomes a mandatory guarded commit; no optional bypass for production callers. An internal raw serializer may exist solely underneath it. It checks current registry/lease identity and open state, frozen row identity, supported metadata, exact on-disk generation/revision, and canonical row identity under the capability gate. Create is explicit and allowed only for a corroborated new objective; a missing expected row refuses.
- Serialize the next row snapshot without first advancing committed state. Use a generation/unique-write-specific temporary filename, preserve flush/fsync → replace → directory-fsync ordering. Advance the capability's committed revision only after the complete durable write succeeds. Every write exception marks `continuity_required` before returning, including a directory-fsync failure after replacement. Do not catch that failure and write an ordinary terminal status through another path.
- All mutations of the canonical shared row, including stage updates, matching progress, reserve/acknowledge and finalization, occur under the same capability gate. Detached row snapshots are observations only. There is one shared row per executing authority, avoiding sibling callbacks with independent stale revisions.
- `_handoff(authority, dispatchId, startCallable)` checks the same predicate after the intent commit and immediately before invoking the existing jobs admission call. Capability revocation/release and handoff serialize through its gate. Do not hold the process-global preparation `_LOCK` across job-store locks, provider calls or job waits. Gate scope ends when the admission call returns/raises, not when the child finishes.
- An accepted child retains its existing job-store ownership/lifecycle. Loss of the preparation capability refuses *new* root handoffs and nested MCP dispatch. It does not kill accepted children or claim that their effects stopped. The root preparation job is handed its exact capability through private in-process state before its thread starts, never inferred from JSON.
- Root handoff uses a private optional `preparation_authority` field on the job record/start seam, excluded from serialization and populated only by `submit`; the preparation backend passes it as a required keyword to `execute`. Direct `execute` without the capability refuses. Existing non-preparation jobs do not require it. A late preparation callback also cannot issue a new `jobs.cancel_job` request after authority loss: guard those calls with current capability and the original accepted child identity. Previously issued cancellation and accepted-child lifecycle stay with the job owner.
- `_release_lease(runId, *, expectedAuthority)` changes the lease registry and handle only when the exact expected object is current. Execution-capacity retirement is the separate expected-slot operation below, not an implication of releasing or retaining a lease. A stale finalizer is an idempotent no-op for successor ownership. Revoke current authority before releasing its own handle; never release another object by ID. Failure handling cannot mask the original refusal with a second write failure.
- Fix every production `_write` caller, including queued-state changes and legacy supersession. Maintenance writes acquire a short-lived physical lease for the exact row, re-read it and commit through their own non-dispatch capability. No maintenance authority grants execution. Legacy writes require the legacy row's own lease; on contention leave it untouched and report/defer reconciliation. Do not hold a partial collection of project/resource locks while waiting.

Lock discipline must be explicit in implementation: acquire the per-authority gate before short registry `_LOCK` sections; never acquire a gate while already holding `_LOCK`. Refactor the current outer `_LOCK` callers accordingly. Do not invoke jobs admission while holding `_LOCK`; job-store code must not call back into preparation while holding its store lock. Review this ordering as part of the later source review.

### Controls and allocation continuity

Move `control`'s pre-submit row update into the lease-owning submit path: read the latest command and row *after* acquiring authority, merge only the permitted deadline fields, then commit. Never merge an entire caller-held row. Preserve `_revise_admission_budget`'s drained-owner requirement and expected allocation revision.

Commands remain separate desired-state records so pause does not require stealing an executing lease. Serialize cross-process command read/modify/write using a dedicated short-lived nonblocking command-file OS lock and a monotonically increasing command revision; preserve untouched fields, fsync before `controlAcknowledged:true`, and distinguish missing-new command from unreadable/corrupt command. For admission use a strict control read: unknown control state blocks handoff; public cached observation may report unavailable with its as-of revision. An admission holds the authority gate while briefly acquiring the command lock for its decision snapshot, then releases that lock before calling jobs. Control writers release the command lock before requesting any authority operation. Never wait for a worker while holding the command lock; contention is a retryable control-observation prerequisite, not an inferred resume.

The handoff gate takes one coherent latest control snapshot. A command committed before that decision is honored. A command racing after that decision governs the next admission; an already accepted child follows the existing drain semantics. `controlAcknowledged` means the command was durably recorded, not that a child stopped. Pause/resume/budget/priority never clear an authority fault or refund reservations. A failed command write cannot report acknowledgement. Stronger cross-host command ordering and durable wake delivery are followups, not achieved here.

### Error and storage-failure semantics

Use a private `_PreparationAuthorityRefused(Exception)` carrying a bounded decision dictionary; it is deliberately not a `ValueError`/`OSError` subclass. Authority faults use `nextAction` values `preparation_authority_lost`, `preparation_continuity_required`, and `preparation_persistence_failed`; these carry `wakeCondition: explicit_preparation_continuity_reconciliation`, run ID, generation, last committed revision and `phase` (`intent`, `handoff`, `acknowledgement`, `checkpoint`, `control`, `initialization`). The distinct no-effect `_PreparationIssuanceWait` and issuance-limit policy refusal have the exact alternative wakes/dispositions defined above; neither implies a lost existing authority. No secrets, arbitrary params or whole ledger in the public refusal. MCP wrappers preserve their existing `provider_authority_lost` / `provider_budget_persistence_failed` values for compatibility and attach the preparation cause; do not turn them into transient failures.

### Capacity retirement and per-row fault isolation (DA-4)

Replace execution-capacity membership's ID-only set semantics with `_ACTIVE: dict[runId, slotToken]`, where the private token captures the exact authority/generation and root admission identity. `len(_ACTIVE)` still implements the existing four-live-coordinator limit; `_LEASES`/`_FAULTS` separately retain physical ownership/quarantine. Queued rows and clean dormant witnesses hold no execution slot. Capture a token before root dispatch and retire only when `_ACTIVE.get(runId) is expectedSlot`, never by ID alone.

Execution handoff and MCP callbacks additionally require that exact slot's authority, not just run-ID membership; maintenance capabilities cannot satisfy it. Guarded non-dispatch maintenance commits require their own physical lease and healthy witness but consume no slot. A duplicate open while the matching active authority is faulted returns its blocked observation; it does not turn membership in `_ACTIVE` into a successful new admission.

`_retire_capacity(expectedSlot)` is idempotent and runs once the corresponding coordinator returns/raises (or the private start seam proves no root worker-start attempt). It only removes that token and wakes admission; it neither closes the physical lease nor releases any job-store resource. A fault before root termination marks authority unusable but does not pretend the root is already finished. A late finalizer or list observer cannot retire a successor token. Remove `list_runs(public=False)`'s current ID-based `_ACTIVE.discard` at `:452–454`; observation may report a failed job but cannot own cleanup. Current root completion paths, including typed refusal before the execute body, must retire their captured token. Child callbacks surviving parent exit retain revoked authority and cannot write/dispatch; their already accepted jobs continue to be capacity/resource-accounted by jobs.

For a successful clean retirement, release only the expected physical lease and retain the healthy witness. For a returned authority/persistence failure, move/retain the exact capability in `_FAULTS`, invalidate the healthy witness, keep its physical lease open, retire its slot only at the completion boundary, and set the admission wake. There is no public force-release. Thus four finished faulted coordinators can retain four leases while a fifth independent healthy coordinator occupies a free execution slot. If four coordinators genuinely have not returned (including hung IO), this first slice does not promise spare capacity; bounded IO execution remains deferred.

Do not pre-read the whole waiting queue through `sorted(_read(key) for ...)`, where one failure aborts the iteration. Snapshot waiting IDs briefly under `_LOCK`, release it, read/classify each row independently, then rank successfully qualified rows. Apply the same per-entry isolation to inventory collection, legacy candidates and startup recovery. On an authority-fault refusal or malformed/unreadable row, keep at most one bounded diagnostic per `(frozenRoot,runId,generation)` and suppress its ordinary poll-based re-admission in `_WAITING`; retain durable notification/tombstone/history, do not acknowledge inventory completion, and continue with other IDs. The separate no-effect issuance wait and issuance-limit refusal use their bounded retry/policy dispositions above, not this fault-suspension branch. Do not attempt a second `_write` to label a failure. Repeated identical observations update neither spending nor event history. A plain OSError in a known authority operation becomes the typed persistence refusal only **after** acquisition-site namespace contention has been translated to the distinct wait; unrelated validation errors remain distinct. Post-write `BlockingIOError` is never reclassified as no-effect contention.

Faulted/suspended rows wait for `explicit_preparation_continuity_reconciliation`; `_ADMISSION_WAKE`, timer ticks, priority changes, new inventory or a resume message cannot clear suspension. New healthy work must still satisfy its own namespace/witness, store, provider and resource prerequisites. Bound diagnostics to the existing visible run limit (100 entries) plus live fault-owner references; bound text to 512 characters and retain no growing stack/row copies per repeated refusal. Evicting a display diagnostic must never discard a fault-owner reference or re-enable authority. This isolates returned failures, not an unavailable sole shared store or uninterruptible holder.
