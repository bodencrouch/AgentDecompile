# P3.1: authenticate one persisted observation under current owner policy

Date: 2026-10-02. Source-only contract. This document is the only owned edit. No owner configuration, keys, revocation files, databases, processes, catalog, compiler, checker or runtime were inspected or operated.

## Decision and completion boundary

Implement **`current-signed-observation-v1`**, a bounded, read-only authentication predicate for one existing native `parity-check` v1 result carrying `Verification.method="parity-binding-v1"`. Its successful output means: the exact operator task, producer result, independently signed verifier verdict and their immutable evidence are authentic, internally consistent and still permitted as an **observation** by the selected current owner policy. It does not mean that the checker execution has qualified implementation/runtime closure, that the observation is a match, or that any candidate source is accepted.

This is the first independent P3 prerequisite. It consumes real existing signatures and CAS bytes; it can have a genuine positive path without waiting for P2, repeating producer investigations, installing a fake provider or claiming all P3 complete. The subsequent native execution-closure predicate and final source/corpus join remain necessary before dashboard connection. Keep existing dashboard provider `not_connected` and verified counts null.

The one missing authority primitive is an **explicitly owner-configured pin to a public admission snapshot**. Existing config can select keys, methods and basis hashes, but cannot express a coherent current policy/corpus-generation/runtime-profile snapshot. Add that narrow configuration boundary; do not obtain its root or pin from a task, result, request, receipt, mutable named pointer or an allegedly signed historical admission object. No live owner provisioning is implied by implementing the loader.

## Owned implementation surface and API

A later P3.1 implementation owns only:

- New `src/agentdecompile_recovery/corpus/current_admission.py`: immutable policy loading, bounded local record/CAS reads and the predicate below. Recovery imports grid, preserving the existing dependency direction.
- Narrow `src/agentdecompile_grid/config.py` addition: frozen `AdmissionConfig`, under `GridConfig.admission`, with `snapshot_path`, `snapshot_sha256`, `policy_id`, `generation`; all unset by default. Configuration validation/documentation includes these fields through the existing dataclass mechanisms. No writer, migration, new log type, private-key capability or default owner pin.
- One focused regression source file if explicitly assigned later. No report/dashboard/provider route, compiler/P1/P2/target edit, materialized-view change or generic verification-loop rewrite belongs to this slice.

Public contracts, implemented concretely rather than with injected trust callbacks:

`load_current_admission(cfg: GridConfig) -> AdmissionRead`

`authenticate_native_observation(cfg: GridConfig, selection: ObservationSelection) -> ObservationRead`

`ObservationSelection` contains only partition plus the selected TASK/RESULT/VERIFIED record digests and result ref. These are untrusted locators, never authority. It cannot supply config, roots, public keys, accepted methods, snapshot hashes, revocations or a verifier callback. The top-level function loads policy itself and reads only cfg's local log/object roots. No externally constructed `AdmissionSnapshot` grants authentication.

`ObservationRead` has `status` (`authenticated`, `unavailable`, `stale`, `failed`), fixed `reason`, immutable `admission_identity`, exact record/evidence refs, the authenticated task/result/evidence bytes, and observation grade. On success explicitly expose `implementation_source_closure=not_evaluated`, `implementation_runtime_closure=not_evaluated`, `source_acceptance=not_evaluated`. No `accepted=true`, verified function count or restored process-local capability is returned.

## Concrete public admission snapshot v1

Use canonical JSON with exact schema `agentdecompile.current-observation-admission.v1`; the entire bytes must hash to `cfg.admission.snapshot_sha256`. The snapshot is authority only through that configured pin. It is not self-authenticating merely because it is JSON or resides in CAS. Its exact fields are:

- `schema`, nonempty `policy_id`, nonnegative integer `generation`, matching configured policy/generation exactly;
- `public_keys`: at most 64 entries selecting existing public trust material under `KeyringConfig.key_dir`. Each contains safe relative filename, file SHA-256, key ID, algorithm=`ed25519`, trusted role and explicit lineage array. Raw `.pub` operator keys require explicit `lineage=[]`; node records require exact matching public metadata and explicitly present lineage. Refuse duplicate/conflicting key IDs, repeated/cyclic/self ancestry and absent referenced ancestor keys. Do not read `node.secret`, `.key`, HMAC secrets or local-node directories;
- `revocations`: the complete selected snapshot in the existing `key_id -> {at, by, reason}` shape, bounded and strict. Every `by` is a selected fleet/operator key; timestamps are finite. An explicitly present empty object is valid only because the whole snapshot is owner pinned. Missing is unavailable/invalid, never inferred empty. The config pin authenticates the complete revocation set; it does not claim individual entries are existing signed revocation records;
- `independence_policy="disjoint-lineage"`; do not silently accept the weaker existing `ancestry` policy;
- `observations`: at most 16 explicit entries, with exact `kind="parity-check"`, `kind_version=1`, `method="parity-binding-v1"`, native checker `verifier_id`, nonempty explicit `basis_hashes`, allowed task-operator/producer/verifier key-ID sets and `profile_id="native-objdiff-observation-v1"`. No wildcard, empty-means-any or caller policy override;
- `corpus_scope`: explicit opaque owner scope ID plus `generation` and immutable `snapshot_ref`, or explicit null for observation-only use. A nonnull scope is an admitted scope declaration, not proof that a parity task names a corpus function. The eventual source/corpus consumer must require nonnull and corroborate its actual read snapshot and unique candidate join. P3.1 never infers corpus binding from it;
- `execution_profiles`: empty for this initial observation-only slice. Future runtime closure uses a separately versioned schema/consumer; nonempty unrecognized declarations refuse rather than producing a fake admitted-runtime claim.

Node public-record compatibility clarification: `worker/identity.py:174` emits `created_at`, `expires_at`, and `previous_key_ids`; `log/signing.py:401` treats these as lifecycle metadata, not signature authorization. The strict loader may accept these existing fields with finite timestamp and bounded key-ID-list validation, pinning the complete file bytes. They cannot grant role, infer trusted lineage from previous IDs, renew a key, or replace the explicit current owner snapshot. This initial reader preserves existing Keyring authorization semantics; it does not introduce an independent wall-clock expiry policy.

The authority is the effective owner config plus selected public-key bytes and the pinned snapshot. Existing verifier scheduling options are included in the captured config identity and checked for incompatibility: a nonempty scheduling basis allowlist may not contradict the selected entry; configured method override/default must resolve to the supported kind path, not an unrelated generic verifier. The policy's emitted method requirement remains exact even when dispatch is `kind`. Do not use a method string as executable-source identity.

All selected TASK, producer, verifier and ancestor keys must remain trusted and unrevoked in this snapshot. Enforce operator role for TASK, producer role from the explicit policy set and verifier role fleet/operator plus its explicit set. Call the existing signature authorization and `keyring.independent(producer, verifier)` on a newly constructed public-only ring. No record's `producer_lineage`/`verifier_lineage` can override snapshot metadata. A changed snapshot, role, lineage, revocation or config generation is re-evaluated for every read.

This is design support for owner admission, not owner admission performed here. If no pin/root/policy is configured, return `unavailable:admission_not_configured`; do not create config, choose default roots from a receipt, ask a result producer to sign its own trust policy, or provision an empty policy automatically.

## Exact P3.1 read and causal tuple

1. Establish one monotonic 10-second cooperative deadline. Bound snapshot to 256 KiB, each public key file to 16 KiB, log to 16 MiB/4096 records, each log line to 128 KiB, result/task envelope to 64 KiB, receipt/evidence object to 1 MiB, raw report to 4 MiB, each COFF input to 64 MiB, total CAS reads to 160 MiB and distinct refs to 16. Use 64-KiB chunks and limit+1 detection. These are initial supported limits, not permission to truncate a valid larger record. Kernel-stalled reads are outside a cooperative deadline guarantee.
2. Read only ordinary local files with no-follow descriptor-relative traversal under owner-configured roots; reject symlinks/nonregular files, unsafe names and unsupported layout/transports. Require supported immutable CAS layout; open nothing with create/write/truncate flags. No `put`, named-pointer lookup, quarantine, touching, repair, replay/materialization, DB connection or remote fallback. Reuse existing validators/canonical encoding/signature functions after strict decoding. Do not call ordinary unbounded `get()` or `LocalFileLog.read()` and then check size afterward.
3. Capture a complete stable selected partition from genesis (`seq=1, prev=""`) through its current complete tail. Check strict outer schema/types, no duplicate JSON keys/nonfinite numbers/coercions, then existing record validation and full predecessor linkage. The initial narrow profile refuses a compacted prefix (`unavailable:raw_history_unavailable`) or torn/changing tail (`unavailable:log_snapshot_unstable`); it does not reinterpret an arbitrary `prev` as a trusted checkpoint. Supporting checkpoint-carried evidence is a future explicit extension, not a reason to change historical readers.
4. Resolve exactly the selected three signed records. Require TASK before RESULT before VERIFIED within that partition, exact partition/spec partition, recomputed task ID, and one identical nonempty basis across all envelopes, spec and result. Authenticate each signature and current key policy. Unrelated records need structural/chain validation, but their retired keys do not invalidate the selected tuple simply by being present. Scan the complete captured partition for currently authorized REFUTED records targeting this exact task/result; any such contradiction fails closed as `conflicting_verdict`. Do not treat absent/untrusted negative records as trusted, and do not silently select a later positive to erase a trusted refutation.
5. The RESULT signer, body producer, immutable result producer and VERIFIED body producer must be identical. The VERIFIED signer/body verifier must be identical and independent of the producer under current trusted lineage. Require record type VERIFIED and body outcome `verified`, selected emitted method exactly `parity-binding-v1`, and result status `OK`. Authenticated diagnostics with `grade=error` can still be valid observations; they cannot become source acceptance.
6. Read the actual result object by the signed `result_ref`, stream-hash bytes and require exact worker `TaskResult.to_record()` schema/canonical encoding for v1. Do not normalize tagged `tasks/results.py` records into untagged worker records while keeping the original hash; that distinct historical encoding is unsupported here until explicitly specified. Check task/basis/producer/status/output-set equality with the signed body. Elapsed duration in log bodies is rounded by the existing producer, so do not demand raw float equality with result metrics; it is diagnostic, not the causal identity.
7. Require exactly one of inline `evidence` and `evidence_ref`; both/neither refuse. A ref is signed content-addressed evidence: bound-read and hash it before parsing. Require the real P1 evidence fields and predicate/scope (`authenticated-checker-observation-v1`, `native-reported-code`, `registered-artifacts-v1`, target completeness false, runtime `not_evaluated`, `compared=["receipt"]`, `reason=receipt_equal`). Authenticate every named proposed/recomputed receipt/raw output plus both task COFF inputs under the fixed caps. Proposed output refs must equal the actual result outputs; proposed/recomputed canonical receipt bytes must agree. Validate the receipt's existing kind/version, basis, verifier ID/flavour, side digests, symbol and grade/status/exit/differences rules against this task and actual bytes; require the signed evidence grade to equal its receipt grade. The receipt has no standalone task-ID field: task identity comes from the signed tuple and these exact side/parameter bindings. Use a lane-local read validator, not `ParityCheck.verify()` (which runs a checker). Do not follow arbitrary additional JSON refs or recursively crawl CAS.
8. Native checker ID is checked against the explicit entry and actual task/receipt; this authenticates what was observed, not today's installed executable. Validate the signature-covered proposed/recomputed raw evidence refs and bytes; do not rerun the checker or upgrade legacy parser semantics. Persisted method/source provenance is not proven by merely possessing the same local method name.
9. Reread/hash the selected authority files and log snapshot and require unchanged identities before returning. Reauthenticate retained CAS bytes if persistent mutation is detected; never return a prior cached positive after a failed current read. Return an immutable authenticated observation plus all content identities, not a `verify_receipt=lambda ...` gate.

The trust model is the owner's configured current policy and local log root. Signatures cannot independently prove that a local owner-controlled history has never been rolled back, or discover a withheld remote revocation. Cross-host rollback resistance requires a separately admitted monotonic authority; P3.1 does not invent one. A request-provided old snapshot cannot select policy because the pin is read exclusively from config.

## Status and future cache contract

| Condition | Result |
|---|---|
| Exact independently signed tuple and current explicit observation policy | `authenticated:current_observation`; match/mismatch/error grade remains distinct. |
| Unconfigured authority, missing key/evidence/history, unsupported transport/encoding, limits/deadline, unstable files | `unavailable` with a fixed specific reason; no numeric zero. |
| Fully authenticated historical observation now excluded by key/lineage/revocation/method/checker/basis/policy/generation rules | `stale` with the disallowed dimension. Missing old key material prevents authentication and is `unavailable:signer_not_available`, not fabricated historical validation. |
| Bad signature/hash, malformed record, causal substitution, duplicate/contradictory fields or trusted conflicting verdict | `failed` with exact integrity/association reason. |
| Snapshot exists but mismatches configured digest/policy/generation | `failed:admission_snapshot_mismatch`; do not fall back to a previous snapshot. |

`admission_identity` is a canonical digest of schema/predicate version, effective admission and relevant grid config, configured pin/policy/generation, actual public-key content/metadata digest, full revocation content, observation allowlist and corpus scope. The observation identity additionally includes full selected signed-envelope byte digests (signatures included), captured log content/tail identity and every consumed CAS ref. Include all of these in any future adapter cache key together with the actual corpus read snapshot/generation and adapter implementation version.

Initial implementation should avoid caching positive authentication altogether. A later cache must reread/revalidate current authority and log identity **before cache lookup**; config reload failure, changed generation, missing policy or unreadable revocations invalidates acceptance immediately. No policy writer or DB update is needed during a dashboard request. The future route's owner-config loader must observe config replacement on each request or supply an already coherent reload revision; a long-lived stale `GridConfig` object is insufficient. Never let a receipt choose that loader/config revision. A cache that cannot establish currentness returns unavailable, not the former count.

## Exact remaining P3.2 premise and smallest execution contract

Do not solve P3.2 in the P3.1 edit. Its remaining premise is **actual execution bound to a currently admitted source/runtime closure**, not missing Ed25519 capability. `target.py:_implementation` reconciles a fixed Python helper closure but explicitly excludes interpreter/native SQLite qualification; P1/P2 explicitly leave broader closure unevaluated. `worker/sandbox.py:run_manifest` imports configured modules into an ordinary Python subprocess and dispatches a kind; its manifest is not a measured, confined runtime. `ContainerSandbox` is declared-only. No installed qualifying sandbox/runtime is asserted here.

The smallest subsequent profile is `linux-x86_64-native-objdiff-region-runtime-v1`, restricted to the P2 contract's `objdiff-3.8.0-native-linux-x86_64-coff-i386-leaf-v1`, existing reference-free target path and the exact official checker digest already specified there. It excludes Node/Wasm and compilation. It cannot qualify `compile-attempt`'s wrapper/Wine/compiler environment or turn `source_contribution`'s native clang observation into the grid compiler receipt. The complete source path will still need a separate actual compile-closure profile (or a separately implemented native compiler producer with its full binding); keep that as an explicit remaining requirement.

Smallest producer/action contract to implement separately:

1. A recovery-owned qualified-execution supervisor consumes immutable P2 task/result/prerequisite refs, an **owner-pinned** runtime-root identity and isolation policy, exact implementation source identity, and selected real verifier identity. Profile selection is config-only. It performs the actual existing P2 verification within that runtime; an old unqualified P2 result can be reverified there, but its old record is not restamped.
2. The root must exhaustively bind the Python executable/stdlib/extensions, SQLite library, every imported recovery/grid/helper/parser module, native objdiff executable and dynamic loader/shared libraries; fixed argv, environment/options, import paths and allowed data/scratch mounts belong to the profile. The root's full ordinary-file inventory, safe symlink resolution and digest must be measured by the owned supervisor, with bounded traversal and an immutable execution view. Read-only source hashes beside mutable code or a caller-provided `complete` manifest cannot qualify loaded code. Enforce no external executable/library/import/config loading and sanitized environment; absent confinement support refuses. Treat the kernel/supervisor and owner-selected host isolation boundary explicitly as trusted, not as discovered by a receipt.
3. Execute from the same pinned read-only view measured by the supervisor; ensure writable scratch cannot supply imports/executables and input mounts are data-only. Verify actual loaded/executed identities, closure stability and process completion around the invocation. Before/after disk hashes alone do not establish loaded-code equality or exclude transient replacement. Source-to-loaded reconciliation must cover the invoked predicate/parser/helper bindings, not only the target lane's present fixed closure.
4. Persist an immutable execution record containing profile/root/source/runtime-policy identities, exact task/result/basis, produced verification/evidence refs, actual measured dependency identity and the supervisor's fixed successful enforcement/measurement outcome. Bind that record into the **real independently signed verifier evidence at collection time**; a later standalone JSON receipt or unrelated signed NOTE cannot retroactively attest the earlier execution. This requires a narrow supervisor-to-verifier-collection evidence contract, with private child IPC/owned job identity checked before signing. Producer execution needing qualification must be bound at its analogous actual collection event, not inferred from verifier output.
5. Expose a separately named owned 8080 catalog action only after source implementation can produce that evidence. Required inputs are explicit immutable refs and configured profile ID; no arbitrary commands, runtime roots, keys or policy from request payloads. An authorized action must corroborate process/work ownership and independent keys before launching; no execution by the read adapter. Source investigation here neither queries a live catalog nor presumes that this action exists.

This is a concrete producer boundary and input contract, not a claim that root confinement or runtime qualification is already implemented. A later P3.2 design must settle the exact supported host enforcement mechanism and root artifact before coding a positive execution path; unsupported host/kernel capability returns unavailable. Owner-selected root/source/runtime pins and actual independent signed qualified executions are still real provisioning/execution premises. They can be pursued without unrelated U11/fleet work and cannot be supplied by a test-only bypass.

After P3.2, the final read adapter must still authenticate compile, target and P2 records and the exact candidate-row/source-to-TU/object/target/parity/current-corpus join specified in `next-acceptance-adapter.md`. P3.1's observation-only `corpus_scope=null` is necessarily insufficient. Fresh whole-image acceptance and runtime readiness remain separate obligations.

## Regression source specifications and permitted review

These cases are specifications only; no tests or proof scripts were run:

- `real_ed25519_current_native_observation`: actual public Ed25519 signatures on the real TASK/RESULT/VERIFIED record schemas, two disjoint admitted producer/verifier lineages, canonical CAS result/receipts/raw evidence and an explicit configured policy pin authenticate. The fixture exercises the actual signature implementation, not a truthy verifier callback. This establishes P3.1 only; live producer/runtime acceptance requires actual qualified evidence later.
