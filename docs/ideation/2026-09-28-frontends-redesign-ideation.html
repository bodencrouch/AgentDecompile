Grounding Context

Codebase Context

One FastAPI backend serves both frontends. The action catalog holds 233 actions flagged danger, mutating or long-running. A single workbench.prepare run already automates the whole ladder, with 13 stages from project inspection to the byte audit. Adding a program to an open project admits that run automatically. Registering a bare binary or opening a locator does not.

The static 8080 UI still carries more than 25 action buttons that trigger work the pipeline does itself. It also shows a second "Compile and verify" ladder with Run buttons over the same stage keys, and a "Run pipeline" Start button that the frontend intent bans. A third surface, the explorer page, has its own "Start workflow" button. Pause, resume and stop are live in the Vite workstation, but not on 8080 or the explorer.

For CodeBrowser parity, the Decompiler and one-hop call trees exist today, and the Listing and Symbol Tree are partial. The Data Type Manager, Memory Map, Symbol Table and Bytes views have backing data but no panel. Program Trees, Defined Strings, Console, Function Comparison, Equates and Relocations have none yet. Nothing links the panels across windows: no shared cursor, no back or forward history, no go-to, no overview bar.

The corpus already links binaries:

  • 291,302 identity bindings across 29 of 90 binaries;
  • 975,077 match rows across 89 directed pairs, 568,688 of them awaiting review;
  • a query-time "cross-build reach" join on the call graph.

Sessions allow only one visible project. The MCP bridge keeps one active locator process-wide, behind a global lock.

In Vite, the live root mounts the workstation only. A richer objdiff-audit tree is unreachable, and the served bundle is stale. Progress numbers disagree by source: 1,372 local recovered rows against 7,233 of 24,242 in a reconciliation snapshot. The whole-image compiler receipt evaluator is a deliberate stub.

External research covered five sources:

  • Ghidra CodeBrowser: the stock tool layout and its help pages. Version Tracking is two tool windows joined by a Matches panel, and only one active program drives the cursor.
  • objdiff and objdiff-web: a unit list and a two-column diff with live re-diff and no Run button.
  • decomp.dev: per-version report files, solid versus hatched bars, a size-weighted treemap and history charts.
  • decomp.me: function scratches with a live match score.
  • Dogbolt, RzWeb, r2web and APKMan: multi-decompiler panes, WASM engines in workers, panels named after the command behind them, and one engine serving both the UI and MCP.

No external tool chains stages, matches identity across builds, distributes compute, or keeps verifiable receipts per region.

Idea 1

1. Match and call graph in context over one join

project-tabConfidence 80%Complexity Medium
Description

Replace the Match tab and its Run match / Re-run / Match function buttons with four linked parts:

  • A project-aggregate endpoint that joins binaries, identities, match status and preparations once.
  • A cross-binary call graph that promotes the existing identity join to a multi-hop, identity-keyed endpoint.
  • A binary-by-binary pair matrix: 89 computed cells, with every other cell reading "not scheduled", distinct from "failed".
  • Match decisions drawn in place: as edges on the same call-graph canvas, and as badges at the function header in Listing and Decompile.

Review keeps Version Tracking's columns (status, type, score, confidence, algorithm). It adds batch decide by pair and score band through the existing batch route. Byte-level objdiff matches and name/signature matches stay labeled differently.

Axis
project-tab
Basis
direct: the call-graph panel docstring "cross-build reach on every node … exists in up to 24 builds at once" (panels/callgraph.py:1-29); live counts of 975,077 match rows, 568,688 in review and 89 directed pairs; router.py:683 match-decide-batch; decomp_match.py:765-767 bytecodeMatchTool: objdiff vs notBytecodeMatch: match-function. external: Version Tracking's Matches and Markup tables.
Rationale
This is the user's headline ask, and "Match (especially)" is the tab they singled out. The backend already computes the join, so the move is exposure and layout rather than new analysis. The batch path turns more than half a million pending reviews into a decision per pair and score band.
Downsides
The join's performance across 90 binaries is unmeasured, so check the query plan before committing to synchronous fetches. Only 29 of 90 binaries carry identity bindings, and the rest must render as explicitly unbound, which takes honest empty states.

Idea 2

2. Zero-trigger contract

pipeline-controlsConfidence 85%Complexity Medium
Description

Make every open, add and register path admit the preparation run on the server. Show a one-line admission receipt: generation and queue position.

Then remove every trigger for work the pipeline owns, across all three surfaces:

  • the more than 25 action buttons on 8080;
  • the shadow "Compile and verify" ladder;
  • "Run pipeline";
  • the explorer page's "Start workflow";
  • the Vite "Prepare analysis…" offer.

Port the live Vite pause/resume/stop control to 8080 and the explorer as the only workflow control, pre-filled from the selected run.

Enforce the rule per mode from the MCP layer's mutating-action classification, so pipeline triggers cannot creep back.

Keep what the pipeline never does: rename, bookmarks, comments, match decisions and the expert command palette.

Axis
pipeline-controls
Basis
direct: two ladders over the same stage keys, the second with onRun=${runLadderStep} (workbench-app.js:6079-6093); runActionButton("corpus.run","Run pipeline"); the explorer page's "Start workflow" button (explorer-page.js:721); auto-admission only on add-program (workbench.py:1131-1136); pause/resume live in PreparationActivity.tsx:43-46, mounted by the workstation.
Rationale
This is the user's rule stated directly: "anything in the pipeline shouldn't be a button". The frontend intent requires pause/resume as the single control. Fixing admission first keeps the removal from stranding a path with no way to start work.
Downsides
The admission and dispatch code (jobs.py, protection.py, preparation.py, catalog.py) carries another owner's uncommitted edits, which the work must coordinate with. Removing buttons from a 7,000-line file needs careful checks of the surviving command IDs and deep links.

Idea 3

3. Project-tab CodeBrowser on one location bus

codebrowser-parityConfidence 70%Complexity High
Description

A browser tab holds a project and shows its binaries as peers, not one active program with hidden siblings. Each binary carries a readiness stamp: local and readable, or blocked on server credentials, with the backend's own next step.

One program-location object drives every connected panel: Listing, Decompile, Symbol Tree, call trees and cross-references. It brings Ghidra's behaviours: back and forward history, go-to, token highlight sync, and a warm/cold indicator in the location header.

A logical-coordinate ruler syncs peer Listings to the same identity where one is bound, and shows empty lanes where none is.

The Listing reads the lock-free database reader and is virtualized. The decompiler stays a lazy, per-function call.

Axis
codebrowser-parity
Basis
direct: today's navigation is "switch to the Functions tab, narrow its own search … then reuse selectRow" (workbench-app.js:5685-5689); the command list has only tab switches, with no back/forward; _dedupe_project_sessions "leave[s] one project visibly loaded" (ghidra_project.py:1445-1495); the single _ACTIVE_LOCATOR global (mcp_bridge.py:20-26). external: CodeBrowser location sync, where one program drives every provider.
Rationale
Ghidra's real limit is one active program per cursor. A project tab with a shared bus removes that limit, which is exactly the user's reason for projects as tabs. It also gives the panels in idea 4 one integration point, instead of per-panel synchronization.
Downsides
It needs a backend correctness fix first: the single active locator must be scoped per call before peers can read at once. Rapid cursor moves must be debounced against the serialized decompiler bridge and cold reads of 27–55 seconds.

Idea 4

4. Full CodeBrowser provider set from existing data

codebrowser-parityConfidence 65%Complexity High
Description

Build the missing providers through one read-only panel factory, docked where Ghidra's stock CodeBrowser tool puts them:

  • Program Trees;
  • Data Type Manager, from the composite types the reader already exposes;
  • Memory Map, from memory blocks;
  • Bytes;
  • Defined Strings;
  • Symbol Table and References;
  • Function Graph;
  • call trees and the call graph;
  • Bookmarks;
  • a read-only Console log;
  • Function Comparison;
  • Equates;
  • Relocations.

Mutating providers (structure editors, byte patching) stay explicit user edits, never pipeline triggers.

Axis
codebrowser-parity
Basis
direct: the Symbol Tree already restricts itself to actions that are not dangerous, mutating or long-running (workbench-app.js:2405-2410); the reader's composite_data_types() and memory_blocks() have no panel consumer. external: the stock CodeBrowser tool layout and the guide's chapters on symbols, types, listing, call trees, memory map, signatures, structures and diagnosis.
Rationale
The user asked for "exact 1:1 full feature parity". Most missing providers lack only a panel, not data, so a factory turns each one into wiring work rather than design work.
Downsides
Parity is wide. Some providers, like Function Graph and Program Trees, need data the reader does not yet expose. The mutating classification lives in the MCP layer's per-tool action lists, not the catalog file, so gating needs care.

Idea 5

5. Vite as objdiff-web over the pipeline

vite-viewsConfidence 72%Complexity High
Description

Rebuild the Vite workstation around objdiff-web's loop:

  • A unit list with live fuzzy-match percentages, from the objdiff report parser already in the codebase, refreshed over the existing event stream, with no Verify button.
  • A two-column diff.
  • A decomp.me-style candidate scratch with a small wall of recent attempts.
  • A stage graph drawn from observed state, where retry appears only on a failed node.
  • A Dogbolt-style multi-decompiler comparison wherever the backend holds several outputs.

It also carries:

  • a spectator view for any caller, human or agent;
  • a roster of distributed-compute workers;
  • cached decompiler text labeled as advisory, with its generation;
  • a version stamp on the served bundle.

Reuse the phase model and stage trace from the unreachable tree by extracting components, never by nesting the old roots.

Axis
vite-views
Basis
direct: decomp_match.py:128-137 parses report units and measures; the event stream in activity.ts; the menu entry corpus.objdiff-check "Verify compiled bytes" (App.tsx:846) duplicates the byte-audit stage; main.tsx mounts only the workstation. external: objdiff-web's watcher-driven re-diff, decomp.me scratches, Dogbolt panes, and RzWeb's one engine serving both UI and MCP.
Rationale
The user named objdiff-web "especially". The data it needs is already parsed server-side. No surveyed tool chains stages or shows distributed workers, which is where this workstation is specific to this project.
Downsides
The served bundle is stale, so nothing lands without a rebuild, which needs a package install. The extraction work touches components with no live importer.

Idea 6

6. One report spine with honest, tier-split progress

progress-publishingConfidence 60%Complexity Medium
Description

Generate one objdiff-shaped report per binary and version, automatically. Feed it into:

  • a decomp.dev-style project card: solid for verified byte-exact, hatched for advisory, with version pills and a size-weighted treemap;
  • a coverage strip under the Listing;
  • per-run splits, instead of a verdict banner that can only ever read "no receipt".

Every number shows its source and generation, through one shared claim badge. Publishing to decomp.dev stays an explicit, separately approved step while its license is unclear.

Axis
progress-publishing
Basis
direct: the claim boundary "Source availability, compilation, and byte verification are separate claims" (recovery_status.py:152); the two-tier index that is "never merged into a single 'recovered' number" (package_readable_index.py); the stub receipt evaluator (byte_parity.py:93-95). external: decomp.dev's report shape, bars, treemap and history.
Rationale
The codebase already refuses a single progress number, and the UI should draw the same tiers. A single report artifact also becomes the input for the eventual automatic publishing.
Downsides
Two sources disagree today: 1,372 local recovered rows against 7,233 of 24,242 in a snapshot. That has to be reconciled before any card is published. Otherwise the spine publishes the disagreement.
